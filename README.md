# sliding-window-rate-limiter

Ограничитель частоты запросов (rate limiter) по API-ключу для шлюза к языковым моделям.
Алгоритм — **скользящее окно (sliding window log)**, состояние в **Redis**, проверка атомарна
благодаря **Lua-скрипту**. Сервис написан на **FastAPI**.

## Зачем это нужно

Шлюз ходит к провайдеру LLM с общей квотой. Без ограничений один клиент может
израсходовать её целиком, и остальные получат ошибки. Поэтому на каждый API-ключ
действует лимит: **не больше N запросов за любые T секунд**.

## Быстрый старт

```bash
cp .env.example .env
docker compose up --build
```

Успешный запрос:

```bash
curl -i -X POST localhost:8000/v1/echo \
  -H "Authorization: Bearer test123" \
  -H "Content-Type: application/json" \
  -d '{"hi": 1}'
```
```
HTTP/1.1 200 OK
x-ratelimit-limit: 10
x-ratelimit-remaining: 9

{"hi":1,"key_id":"ecd71870d196"}
```

`key_id` — первые 12 символов SHA-256 от ключа: по нему удобно различать клиентов в логах,
а сам ключ в ответ не попадает.

11 запросов подряд при лимите 10:

```bash
for i in $(seq 1 11); do curl -s -i -X POST localhost:8000/v1/echo \
  -H "Authorization: Bearer test123" -H "Content-Type: application/json" \
  -d '{"hi":1}' | grep -iE "HTTP|RateLimit|Retry"; done
```
```
HTTP/1.1 200 OK
x-ratelimit-limit: 10
x-ratelimit-remaining: 9
...
HTTP/1.1 200 OK
x-ratelimit-limit: 10
x-ratelimit-remaining: 0
HTTP/1.1 429 Too Many Requests
x-ratelimit-limit: 10
x-ratelimit-remaining: 0
retry-after: 60
```

> uvicorn отдаёт имена заголовков в нижнем регистре (по HTTP они регистронезависимы),
> поэтому в `grep` нужен флаг `-i`.

Остановить: `docker compose down`.

### API

| Метод и путь     | Описание |
|------------------|----------|
| `GET /health`    | `{"status": "ok"}`, без авторизации и без лимита |
| `POST /v1/echo`  | Возвращает присланный JSON-объект + поле `key_id`. Нужен `Authorization: Bearer <key>` |

Коды ответа `/v1/echo`:

| Код | Когда |
|-----|-------|
| 200 | Запрос разрешён. Заголовки `X-RateLimit-Limit`, `X-RateLimit-Remaining` |
| 401 | Нет заголовка `Authorization` или формат не `Bearer <key>` |
| 422 | Тело — не JSON-объект (например, массив) |
| 429 | Лимит превышен. Заголовки `X-RateLimit-*` и `Retry-After` (секунды) |
| 503 | Redis недоступен (см. «Ограничения») |

## Переменные окружения

| Переменная                  | По умолчанию               | Описание |
|-----------------------------|----------------------------|----------|
| `RATE_LIMIT_REQUESTS`       | `10`                       | N — сколько запросов разрешено за окно |
| `RATE_LIMIT_WINDOW_SECONDS` | `60`                       | T — длина окна в секундах |
| `REDIS_URL`                 | `redis://localhost:6379/0` | Адрес Redis (в docker-compose — `redis://redis:6379/0`) |

Читаются через `pydantic-settings` из окружения и файла `.env`.

## Как работает алгоритм

### Скользящее окно

Для каждого ключа храним время каждого разрешённого запроса. Новый запрос разрешаем,
если за последние T секунд (считая от «сейчас») запросов меньше N.

```
N = 3, T = 10 с

время:   0    4    6    7         10        14
         |    |    |    |          |         |
запросы: A    B    C    X(429)     D(200)    E(200)

в t=7:   окно (-3; 7]  -> A, B, C       = 3 -> отказ
в t=10:  окно ( 0; 10] -> B, C          = 2 -> D разрешён (A вышел)
в t=14:  окно ( 4; 14] -> C, D          = 2 -> E разрешён (B вышел)
```

Окно «едет» вместе со временем, поэтому места освобождаются **по одному**, ровно когда
конкретный старый запрос выходит из окна. При **фиксированном** окне (счётчик на «минуту
00:00–00:59») клиент может сделать N запросов в конце одной минуты и ещё N в начале
следующей — 2N за пару секунд. Скользящее окно так не позволяет.

### Почему sorted set

Ключ Redis: `ratelimit:<sha256(api_key)>` — сам ключ в Redis не хранится.

В sorted set у каждого элемента (member) есть число (score). У нас:

- **score** — время запроса в миллисекундах;
- **member** — `"<время>-<uuid>"`. Суффикс-uuid нужен, потому что member уникален:
  два запроса в одну миллисекунду без него «склеились» бы в одну запись.

Sorted set упорядочен по score, поэтому всё, что нужно, делается одной командой:

- `ZREMRANGEBYSCORE` — удалить всё старше окна;
- `ZCARD` — сколько запросов в окне;
- `ZRANGE key 0 0 WITHSCORES` — самый старый запрос.

### Почему Lua (атомарность)

Наивная реализация на Python делает несколько отдельных команд:

```
count = ZCARD key        # 1
if count < limit:        # 2
    ZADD key now member  # 3
```

Если два запроса одного клиента придут одновременно (два воркера или два корутина),
оба выполнят шаг 1, оба увидят `count = 9 < 10`, и оба сделают `ZADD` — в окне станет
11 запросов. Это классическая гонка **check-then-act**.

Redis выполняет Lua-скрипт **целиком, не вклиниваясь** другими командами. Поэтому
«удалить старые → посчитать → добавить» — одна неделимая операция, и гонки нет. Тест
`test_concurrent_*` шлёт 50 одновременных запросов при лимите 10 и проверяет, что
разрешено ровно 10 (в Docker тот же тест гоняется и на настоящем Redis).

Скрипт регистрируется через `register_script`: Redis хранит его по SHA-хэшу, и клиент
вызывает `EVALSHA`, не пересылая текст скрипта каждый раз.

Шаги скрипта (`app/limiter.py`):

1. `ZREMRANGEBYSCORE key 0 (now - window)` — удалить устаревшие записи;
2. `ZCARD key` — посчитать текущие;
3. если `count < limit` — `ZADD`, `PEXPIRE key window` (ключ сам исчезнет, когда все
   записи устареют), вернуть `allowed=1, remaining = limit - count - 1`;
4. иначе — вернуть `allowed=0, retry_after_ms = oldest + window - now`.
   **Отклонённый запрос в окно не добавляется**, иначе клиент, который продолжает
   стучаться, продлевал бы себе блокировку бесконечно.

Время `now` передаётся в скрипт из Python через функцию-часы `clock`. В тестах её
подменяет `FakeClock`, и сдвиг окна проверяется мгновенно, без `sleep`.

### Как считается Retry-After

Самый старый запрос в окне (`oldest`) выйдет из него в момент `oldest + window`.
Значит ждать надо `oldest + window - now` миллисекунд. Заголовок `Retry-After` —
целые секунды, поэтому **округляем вверх** (если ждать 6.8 с, а мы скажем 6, клиент
придёт рано и снова получит 429) и берём **минимум 1**.

### Граница окна

Окно — полуинтервал `(now - T; now]`. Запрос, сделанный **ровно T секунд назад**, уже
**не считается**: `ZREMRANGEBYSCORE key 0 (now - window)` удаляет записи со score
`<= now - window` включительно.

Это согласовано с `Retry-After`: если сказать клиенту «приходи через `oldest + T - now`»,
то в этот момент старый запрос как раз окажется на границе и будет удалён — клиента
пропустят. Тест: лимит 1/10 с, запрос в t=0; в t=9.999 — 429 с `Retry-After: 1`,
в t=10.000 — 200.

## Тесты

**Основная команда** — в Docker, ничего не нужно ставить локально, и это единственный
вариант, где интеграционный тест работает с настоящим Redis:

```bash
docker compose run --rm api pytest
```

Локально (нужны Python 3.12+ и GNU make), одинаково на Linux, macOS и Windows:

```bash
python3 -m venv .venv          # Windows: python -m venv .venv
make install
make lint
make test
```

Активировать venv не обязательно: `make` сам находит интерпретатор — из активного venv,
из `./.venv` или `python3` из `PATH`. Другой интерпретатор можно передать явно:
`make test PYTHON=/path/to/python`.

Юнит-тесты используют `fakeredis[lua]` (Lua выполняется внутри fakeredis) и подменные
часы, поэтому Redis для них не нужен. Один интеграционный тест конкурентности работает
с настоящим Redis: в Docker он выполняется, локально без Redis — пропускается.

Что покрыто:

| Сценарий | Тест |
|----------|------|
| N запросов → 200, `Remaining` уменьшается до 0 | `test_under_limit_*` |
| N+1-й → 429 и `Retry-After` > 0 | `test_over_limit_*` |
| Сдвиг часов на T → снова 200 | `test_window_slides_*` |
| Частичный сдвиг освобождает ровно вышедшие места | `test_partial_slide_*` |
| Запрос ровно `now - T` не учитывается | `test_boundary_*` |
| Разные ключи независимы | `test_different_keys_*` |
| Нет / неверный `Authorization` → 401 | `test_missing_or_malformed_authorization_returns_401` |
| Точное значение `Retry-After` | `test_retry_after_exact_value` |
| Отклонённые запросы не продлевают блокировку | `test_rejected_requests_do_not_extend_block` |
| 50 одновременных запросов, лимит 10 → ровно 10 | `test_concurrent_*` |
| Ключ в Redis захэширован, есть TTL; 503 при падении Redis; 422 на не-объект | прочие |

## Структура

```
app/
  config.py    # Settings (pydantic-settings)
  limiter.py   # Lua-скрипт + SlidingWindowRateLimiter
  auth.py      # dependency: Bearer-ключ -> 401
  main.py      # create_app(): /health, /v1/echo; лимитер через Depends
tests/
  conftest.py  # FakeClock, fakeredis, HTTP-клиент
  test_limiter.py
  test_api.py
```

Глобальных синглтонов нет: `create_app()` создаёт клиент Redis и лимитер в `lifespan`,
роут получает лимитер через `Depends(get_limiter)`, а тесты подменяют его через
`app.dependency_overrides`.

## Ограничения и что можно улучшить

- **Память O(N) на ключ.** Храним отметку каждого запроса в окне. При N = 10 это
  копейки, но при лимитах вроде 10 000/час это уже 10 000 элементов на ключ.
  Альтернатива — **sliding window counter**: два счётчика (текущее и предыдущее
  фиксированное окно), оценка `prev * (1 - доля_прошедшего) + curr`. Память O(1),
  но результат приблизительный. Ещё вариант — token bucket / GCRA.
- **Одинаковый лимит для всех ключей.** В реальном шлюзе лимиты зависят от тарифа:
  нужно хранить их, например, в БД/Redis по ключу и передавать `limit`/`window`
  в скрипт (он уже принимает их аргументами).
- **Лимит только по числу запросов.** Для LLM честнее ограничивать ещё и токены —
  тот же sorted set, но с «весом» запроса.
- **Fail-closed.** Если Redis недоступен, отвечаем 503: лучше отказать, чем
  перерасходовать квоту. Для некоторых сервисов уместнее fail-open (пропускать и
  логировать) — это зависит от бизнеса.
- **Часы.** `now` берётся с часов API-сервера. Если у разных инстансов часы
  расходятся, окно «плывёт» на величину рассинхрона. Можно брать время из самого
  Redis (`TIME` внутри скрипта), но тогда тестам сложнее подменять время.
- **Redis Cluster.** Скрипт трогает один ключ, поэтому работает в кластере как есть.
